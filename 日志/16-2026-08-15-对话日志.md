## 一、RAG 进阶 — 混合检索（RRF）

把昨天（8/14）的 TF-IDF + bge 双路检索，升级成**混合检索**，加进 `rag.js` 的 `--embedder hybrid`。

- **RRF 倒数排名融合**：`score = 1/(60 + 名次)`，两路各算一次加起来
- **为什么用名次不用分数**：稀疏分 ≈0.05、稠密分 ≈0.4，直接加会被 bge 碾压；名次无量纲，第 1 名恒为 1
- **为什么用倒数**：排名收益递减，让「两路都进前列」的菜反超「单路第一」

**实测**：「鸡蛋灌饼」两路都进前 5，RRF 融合后反超只在 bge 排第 1 的「蛋炒饭黄金版」——和 8/14 手算完全一致。

详见 `AI系统学习/06-rag/学习日志-2026-08-15.md`。

## 二、掌厨接入语义搜索（bge 懒加载）

把 rag.js 的语义检索真正接进掌厨 App，不是停在独立脚本。

### 架构决策（静态站无后端的关键约束）

1. **必须自托管模型**：hf-mirror 的 CORS 只放行自身域名，浏览器直连会被拦 → q8 模型提交进仓库，同源加载
2. **必须量化**：fp32 模型 91MB，q8 量化 23MB 才可接受
3. **懒加载**：页面启动不碰模型，打开 AI 助手才后台 `init()`，未就绪走关键词兜底

### 落地方式

- 预计算 159 道菜的 bge 向量 → `data/recipe-vectors.json`（1.64MB → 590KB）
- 浏览器端 `semantic-search.js` 只算查询向量，跟预计算向量做点积
- SW v6：`/models/` 大文件走无超时通道（否则 3 秒超时打断 23MB 下载）

详见 `cooking-app/开发日志.md` 8/15 条目。

## 三、推荐卡片多选修复（结构化 id 替代文本匹配）

**问题**：AI 推荐 4 道菜，但只有 3 个跳转按钮（连续两次：早饭/健身场景）。

**根因**：从 AI 文字回复里「抠菜名」做文本匹配，AI 常缩写菜名——「蒸水蛋（鸡蛋羹）」写成「蒸水蛋」、「蒜蓉西兰花炒虾仁」写成「蒜蓉西兰花」，`indexOf` 必然漏配。

**修法（治本）**：不靠文本猜，直接用结构化 id。

- `cookingAgent` 返回值从 `string` 改为 `{ reply, recipeIds }`
- 语义/标签检索的 id 从 `preSearch` 带出；agent 循环的 id 从工具返回里收集（`collectRecommendationIds` + `agentLoop` 收集）
- `getAiRecommendation` 按 id 渲染多张卡片，点哪道进哪道
- 文本匹配 `extractRecommendedIds` 降级为兜底，并加了核心名匹配（剥「（...）」后缀）

## 四、同义词映射（标签意图检测）

**问题**：bge 语义向量对口语词匹配弱——搜「想吃健身吃的」返回「蛋炒方便面/鸡蛋灌饼」，「健身」对不上「减脂」标签。

**修法**：新增 `TAG_INTENTS` 同义词映射表 + `detectTagIntent()`，`preSearch` 优先级改为：

```
食材列表 → 标签意图（同义映射）→ 语义检索 → 关键词兜底
```

### 覆盖（18 标签全包含）

| 类别 | 示例口语词 → 标签 |
|------|------|
| 健康 | 健身/减肥/瘦身/增肌/低卡/清淡/健康 → 减脂 |
| 快手 | 简单/省事/好做/懒人/容易做 → 快速 |
| 早餐 | 早饭/早点/早上吃 → 早餐 |
| 下饭 | 开胃/配饭/拌饭 → 下饭 |
| 请客 | 聚会/待客/年夜饭/招待 → 宴客 |
| 凉菜 | 凉拌/冷菜/冷盘/爽口 → 凉菜 |
| 喝汤 | 煲汤/喝汤/炖汤 → 汤羹 |
| 菜系 | 川味/麻辣→川菜；广式/广东→粤菜；湖南→湘菜；山东→鲁菜；淮扬→苏菜… |

### 关键设计

1. **只放「意图词」**，不放单字食材词（汤/虾/鱼）——避免「鱼香肉丝」误判成海鲜
2. **具体菜名不误判**——「番茄炒蛋」「皮蛋瘦肉粥」返回 null，走语义/关键词精准找到那道菜
3. **顺序即优先级**——一个查询命中多标签取靠前的（「麻辣下饭」取川菜）
4. **可扩展**——想加新词，往对应标签 `words` 数组补一项即可
5. **22 条测试全过**

## 七、经验记录

> 1. **融合用「名次」不是「分数」**——两路分数差一个数量级，直接加会退化成单路；名次无量纲、第 1 名恒为 1，才公平可比。
> 2. **语义检索 = 预计算语料向量 + 运行时只算查询向量**——语料侧离线算好存 JSON，浏览器只下个小模型算查询，这是纯静态站做 RAG 的正确姿势。
> 3. **自托管是绕过镜像 CORS 的唯一可靠手段**——要么花钱买支持 CORS 的 embedding API，要么把模型提交进仓库同源加载。
> 4. **文本匹配永远不可靠**——AI 会缩写菜名（「蒸水蛋（鸡蛋羹）」→「蒸水蛋」），靠抠文字匹配必然漏。正确做法是把结构化 id 一路带出来，文字只做兜底。
> 5. **语义向量对口语词匹配弱**——「健身」对不上「减脂」。标签体系是「字典语言」，用户是「口语语言」，中间需要一张同义词映射表来翻译。
> 6. **同义词映射只放「意图词」，不放单字食材词**——「鱼香肉丝」不是海鲜，「汤/虾/鱼」这种单字在具体菜名里会误命中。
> 7. **SW 的 3 秒超时陷阱**——静态站里大文件（23MB 模型）下载会超过超时阈值被 SW 打断，要单独给大文件开无超时通道。
